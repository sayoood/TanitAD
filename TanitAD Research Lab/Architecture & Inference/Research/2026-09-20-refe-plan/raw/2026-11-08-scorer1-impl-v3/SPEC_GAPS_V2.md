## Amendment 1 item 3 - RESOLVED: an invalid proposal's label cannot enter a pair
* The label schema has no per-proposal validity field. `onpolicy_relabel_pdm.py:58-64` scores ALL 64 plans of a set in one `score_plans` call inside a try; an exception drops the WHOLE set (`failed += 1`, no record). `train.py:526` (`ok_len`) rejects a record whose six components are not 64 long, `train.py:533` stores `np.clip(...)` of all six; `--require-pdm` (scorer_finetune.py:1394 area) then serves only sets that carry a record. So a served set has a real label for every proposal.
* `p1_diag`'s `valid` is a flag of the navtest TABLE (`sel_common.py:91`, `T["valid"]`), not a training-label field.
* The one residue is a NON-FINITE label (`np.clip` keeps NaN) or a non-finite proposal: `y_i > y_j` and `|v_i - v_j| / v0 >= dv` are both False on NaN, so such a proposal forms no pair. Pinned by `test_pair_loss.py` T8 (NaN labels and NaN speeds; they never appear in `select()`'s indices).
* Therefore no exclusion step was added (an exclusion would be a second code path with nothing to exclude).
