## Root cause found by reading the code (MEASURED on CPU, not on the pod)
`fwd()` stores the head's output in `cap["aux"]` and the tensor it read in `cap["aux_ctx"]`. Under HB that tensor is the output of the LoRA ViT-L trunk COPY, so it keeps the copy's whole autograd graph alive until the NEXT `fwd()` overwrites it, and that overwrite happens only after the next forward has built a second graph. The preflight runs `fwd()` once (G3/G2), then again inside G12, again inside G21 (and G21's two-update probe). Measured through the real preflight on the HB stub, number of trunk-copy graphs still alive when each fresh forward starts: **original [0, 1, 1, 1], patched [0, 0, 0, 0]**. The failing frame (`g12_probe -> fwd -> select_actx -> ctx`) is the second forward. Caveat: the "allocated 38.03 vs 37.78 GiB at batch 4 vs 8" figures are the allocation at the moment of failure (capacity minus fragmentation minus the request), so they do not prove micro-batch independence; the doubling is a code-level finding and the GiB it frees is ESTIMATED only (one graph at batch 4, size unknown; the per-gate peaks from lever 2 will give it).

## Levers
1. **Allocator** (`vdac_pod.sh`): `ALLOC` is set to `expandable_segments:True` for HB-s0 and HB-SHUF only, and `export PYTORCH_CUDA_ALLOC_CONF="$ALLOC"` runs after `teacher_env.sh` and before every python launch (preflight, mutate, mutate_ego, run), so the trainer inherits it. Evidence (`test_vdac_hbmem.py`, fake python printing its own env, all 4 modes x 7 arms): value present for HB-s0 and HB-SHUF, `UNSET` for HA-s0/HA-s1/HA-SHUF/HC-s0/HC-SHUF. `MODE=argv` sha256 of all 7 arms, patched vs tip: identical (HA-s0 76f424b6, HA-s1 e52913bc, HA-SHUF 1992f7de, HB-s0 bb933459, HB-SHUF 6815d8eb, HC-s0 232c2131, HC-SHUF 5a0f921b), and each equals `launch_gate.vdac_argv`. torch 2.7.1 support: expandable segments exist since torch 2.1 on Linux (INHERITED, pod venv-teacher not touched; this dev box has torch 2.11, which cannot confirm 2.7.1). It does not change values, only where blocks are placed. It also addresses the 5.74 GiB reserved-but-unallocated.
2. **Instrument** (`aux_hb.MemGates`, used as the preflight `gates` dict): one `preflight_mem` row per finished gate in `preflight.jsonl` (`max_allocated_bytes`, `max_reserved_bytes`, `reserved_bytes`, `allocated_bytes`), peak reset between gates; null on CPU. An unhandled exception (an OOM) appends a `preflight_mem_fail` row (last finished gate, error, last 6 frames, peak since). `gpu_mem_gb` keeps the whole-preflight peak through a running maximum. `gate_checks` parses the log by event and ignores unknown events (read at `gate_checks.py:1470-1495`).
3. **Hygiene** (`aux_hb.release_aux_graph(cap)`, three call sites, HB only): drops `cap["aux"]`/`cap["aux_ctx"]` (+ `gc.collect`, `empty_cache`) before G12, before G21, and at the start of G21's state probe. Every reader of those keys (`aux_backward`, G12 tap row, G19 `_vdac_run`) reads right after its own `fwd()`, so no value changes. I did NOT touch `.grad` of model/armB/base or other references: G12's `run_arm` deep-copies armB and G2 needs them, and the stale graph is the only large one.
