## E1 Where the rule sits (the card: "a wrapper around its planner")
* `rollout()` (:399-424) calls `plan = planner(batch)` (:414), then `hook(n, batch, plan, states)` (:417-418), then `st.commit_plan(pl, m)` for each window (:419-423). The planner sees the batch of one tick, executes nothing; `commit_plan` (:181-192) executes the first m knots of the plan it is given. So the rule is applied to the plan array the planner returns: the hook (the tick dump) and the commit both see the ruled plan, and the dump keys `ol` (tick-0 plan, :415-416, :552) and `ticks.plan` hold the ruled plan. The model outputs `tau` and `P` of the tick dump are the model's own (unruled).
* `cmd_run` (:501-583) is not copied. The wrapper `v8f_t1_eval_rule.py` imports the pinned module from `--tree` (importlib, by file path) and replaces two module globals before calling `cmd_run`: `model_planner` (:280, called at :530, returns the model planner; the wrapper returns a `RulePlanner` that calls the original and then the rule) and `rollout` (:399, called at :535/:537 for the model and at :540 for the P10 floor; the wrapper binds the states list to a `RulePlanner` and calls the original; the floor planner is not a `RulePlanner` and is rolled unchanged). Nothing in the pinned file is edited.
* The `RulePlanner` exposes `keys_read`, `aux`, `heads` of the planner it wraps (properties), because `rollout` tests `hasattr(planner, "keys_read")` (:410), `TickRecorder.__call__` reads `planner.aux` / `planner.heads` (:348-351) and `cmd_run` reads `mp.keys_read` (:538).
* Rule off: `--dist-rule off` installs nothing: `cmd_run` runs with the pinned globals. A rule that is on but inactive on a tick returns the plan array of the base planner itself (same object, bit for bit).

## E2 Per-window state at a tick (what the planner knows besides the batch)
At a tick `st.j` is the tick frame (cache step) because the planner runs before `commit_plan` (see TickRecorder docstring :325). Window start t0 = `st.t0`; tick step k = j - t0 (0, m, 2m, ... < 30); clip index ci = `st.ci`.
* v0 (rolled ego speed): `batch["p10f"][b, -1, 0]` as float64: the measured ego speed the prior reads (:354, the same value `TickRecorder` stores as `v0`).
* Logged path of the window: `g_log = st.d["gt"][t0]` [30,2], the logged future in the ego frame at t0 (`d` is the shallow dict of :166; `gt` is not an EGO key, so it is the logged array; the dump key `g` is the same array, :548, :555). Used only to define progress, as in card ADD25 (HEADWAY_DEFS D4). Privileged geometry of the logged driver: it is used by BOTH sources (also `head`), by card section 2 ("stands in for re-perception"). It is named in the limits.
* a_l(k) = arc coordinate of the logged point P_k of `g_log` (0 at k = 0): `headway_read.logged_arc` (headway_read.py:87-90) for k >= 1. a_m(k) = progress along the extended logged path of the rolled ego position at step k: `headway_read.progress` (:93-111). The rolled position at step k in the t0 frame is `fk.gt_waypoints(st.track[0::2], [t0], [k])` = the same function `exec_in_ego` uses to build the dump key `cl` (:131-133); at k = 0 a_m = a_l = 0 by definition (the projection of the origin carries 1e-13 of rounding and is overwritten with 0.0). `dist_rule.py` carries a verbatim copy of `_path_frame`, `logged_arc`, `progress` (the pod has no `headway_read.py`); `test_dist_rule.py` asserts the copy equals the original on random paths (max abs diff 0.0) and that, after a rollout, a_m of the log equals `progress(g, cl[k-1])` of the dump.
* v_l(j) (logged ego speed at the tick frame): the cache speed row `base["v"][j]` of the logged clip (the array `wm_speed` is built from, v8f_mini_data.py:659-662 region; at or before the tick: frame j itself). The dump definition D5 (step speed from `g`) is not used because it does not exist at k = 0. A non-finite value makes the rule inactive on that tick (counted `src_bad`).
* Gap of the rolled ego: g0 = g_src + a_l(k) - a_m(k) (card). v_L = max(0, v_l(j) + c_src).

## E3 The plan array and arc lengths (the card: "a_P(i) the arc length of the plan along its own path")
The plan `plan` [30,2] is `out["traj30"]` (:294): 30 knots at 0.2 s in the ego frame at the tick (origin = ego now, NOT in the array; the earlier rule `rule/RULE_DEFS.md` a. found the same layout). The path is the polyline [0, plan[0], ..., plan[29]]; a_P(0) = 0 and a_P(i) = cumulative length to knot i (i = 1..30), as in `rule/stop_shield.py::path_of` (:71-83). Beyond the last knot the path continues straight along the last non-degenerate segment (`point_at`, :91-104), x axis if there is none. The new plan is the polyline sampled at a'(i); where a'(i) == a_P(i) exactly the original knot is kept (so an unchanged step is bit for bit the input).
Projection in lag form: l(i) = a_P(i) - a'(i), l(0) = 0, a_w(i) = a_P(i) - l(i-1) (algebraically the card a_w = a'(i-1) + (a_P(i) - a_P(i-1)); the lag form makes an unbinding step reproduce a_P(i) with no rounding). Cap a_c(i) = s_L(i) - max(D, TAU * v'(i-1)), floor a_f(i) = a'(i-1) + max(0, v'(i-1) - B_MAX * 0.2) * 0.2, a'(i) = max(a_f, min(a_w, a_c)), v'(i) = (a'(i) - a'(i-1)) / 0.2, v'(0) = v0, a'(0) = 0, s_L(i) = g0 + v_L * 0.2 * i. n = 30 steps are projected, the first m (= 10 in the banked dumps) are executed; the tick log records both counts.
* Saturated step (counted): a_c(i) < a_f(i) and a_c(i) <= a_w(i): the cap would hold the ego below the braking limit and the floor decides. `sat` = count over all 30 steps, `sat_exec` = count over the executed first m steps. Separately counted, `lift`: steps where a_f(i) > a_w(i), i.e. the floor is above what the plan itself wants (the plan slows faster than B_MAX, or its first step is more than 1.2 m/s below the measured v0), so the card formula advances the plan beyond its own wish there.

## E3b Finding on the floor (written before any rollout of a card arm; MEASURED only as a 16-window CPU smoke of checkpoint P_s0, `tmp/smoke`, no card number)
In the card form a'(i) = max(a_f, min(a_w, a_c)) the floor acts on every active tick, not only when the cap binds: wherever a_f > a_w the new plan is AHEAD of the plan the model issued. On the smoke (16 windows, 48 ticks, 14 active) the card form with the label source changed 10 active ticks, 55 steps with `lift`, and moved the rolled path of 5 of 16 windows; the constants of control r2 (`never`) changed 8 active ticks and 5 windows by lift alone, none by the cap. So r2 as written (`never` equal to `off` bit for bit) cannot hold on real plans, and the label-rule effect mixes cap slowing with floor lifting. Builder option `--floor cap-only` (default `card`, the card as written): a'(i) = min(a_w(i), max(a_f(i), a_c(i))) = the floor limits how hard the cap can slow, and never lifts a plan above its own wish. Where no step has a_f > a_w the two forms are equal (tested on random plans); on the same smoke `never` with `cap-only` equals `off` bit for bit (0 of 16 windows differ). `cap-only` is NOT the card: reading arms with it needs a card amendment by the lead; the tool only provides it. Every rule log carries `lift` and the run records the floor option.
* Active: source present, g_src <= 60 m (card: inactive above 60 m; there is no lower bound, the head can output a negative gap and then the cap forces braking), and g_src, g0, v_L, v0 all finite. Otherwise the tick is inactive and the plan is returned untouched.

## E5 Modes of `--dist-rule`
* `off`: nothing installed (= the pinned tool).
* `label`, `head`: the rule of the card with that source.
* `never`: label source, constants D = -1e9, TAU = 0 as written in control r2. FINDING (written before any rollout of a card arm): with TAU = 0, max(D, TAU * v') = max(-1e9, 0) = 0, so the cap is s_L(i), the imagined lead position with zero margin, not an unreachable bound; and the floor of E3 applies on active windows (E3b: it lifts). So `never` equals `off` exactly on windows where no step of the plan reaches the lead position and no step has a_f > a_w, and differs on the others (contact windows: card ADD25 C about 0.045; lifted plans: E3b). With `--floor cap-only` only the contact windows remain. `test_dist_rule.py` shows both: equality on a free-road case and a difference on a plan through a stopped lead. The tick log has `changed` per tick so the lead sees exactly which windows differ.
* `plumb` (added by the builder, not a card mode; name for the lead `<BASE>RM_s<seed>`): label source, cap and floor both absent (a_c = +inf, a_f = -inf) so that a' = a_w and every plan is returned exactly. It exercises the whole wrapper path (source values, log, plan replacement code) with a guaranteed identity, which is what r2 is meant to check. Whether `never` or `plumb` is read as r2 is the lead's call; both are reported.
* `push` (control r3): label source, active as `label`, the cap replaced by a push: a'(i) = a_P(i) + 0.5 * 0.2 * i (the plan advanced along its own path by 0.5 m/s times the elapsed time), no floor (the planted advance of HEADWAY h2 at 0.5 m/s).
