## A. The data path of `train` (card section 2: "the data set, exclusion, window layout, labels")

* **A1 Built by the trainer's own functions, not re-implemented.** `tok_probe.py train` imports the trainer module and calls `TR.build_parser()` (TR:134), `TR.make_config(a)` (TR:366, gives hmax 16 for arm M2b), `TR.build_data(a, cfg)` (TR:2691-2754: manifest, join, `--exclude` 540:600 at TR:2716-2721, window list `train_windows` at TR:2748-2749, ClipStore at TR:2747). The dataset object is built with the three lines of TR:2819-2821 (`D.V8FMiniWindows(..., lead_sup=cfg.lead_sup == "on")`), restated because the trainer has no function for them. Nothing of the data path is re-implemented.
* **A2 The argv.** The default `--trainer-argv` is the argv record of LSD_s0 as given by the lead, pod paths included (`--arm M2b --seed 0 --grid pool4x10 --wm-state grid --wm-cell-dim 16 --lead-sup on --w-lead-sup 1.0 --lead-sup-detach on ... --batch 64 --steps-mult 4`); `--out` and `--device` of that argv are replaced by the tool's own. The flags `--lead-sup-detach on` and `--wm-state grid` are parsed but have no meaning for a probe that has no model; `--lead-sup on` and `--w-lead-sup 1.0` are used (labels on, weight 1.0). The tool refuses to run when `cfg.lead_sup != "on"`, `cfg.lead_hist != 5`, `cfg.w_lead_sup <= 0`, or when the built dataset has no lead labels or one of the label counts (presence, gap, closing) is 0 (as `TR.bad_lead_sup`, TR:1070-1077).
* **A3 The batch stream.** One `D.ChunkedSampler(wins, a.batch, seed=a.seed, chunk=max(4, min(48, info["lru"] - 2)), max_age_t, max_age_s)` (TR:2851-2852), epochs 0, 1, ... in order, each batch collated by `D.collate([ds.item(*w) for w in idx])` through the trainer's `Prefetch` (TR:2757, depth 3, one thread), as the loop does (TR:3037-3045). The same collated batch feeds all arms of the process in the same step, so "the same batches" holds by construction. The batch carries `feats` [B, 16, 40, 1024] float16, `frame_ok` [B, 16], `lead_pres`, `lead_gapm`, `lead_clos` [B, 16] (D:660-673, D:707-721). The probe's forward gets `feats` only.
* **A4 The number of steps.** `total = a.steps or S * a.steps_mult` with `S = ceil(n_windows_all_clips / batch)` (TR:2849-2850) = 19,164 for the argv above (4,791 x 4). The tool writes `S`, `total`, `n_windows`, `n_windows_all_clips`, `train_sha256`, `train_window_list_sha256` and the label `sha256` to `train_meta.json`, so that the lead can compare them with `summary.json` of LSD_s0. `--expect-steps 19164` (the pod script passes it) refuses a run whose computed total differs. `--steps N` is the trainer's own override (TR:299) and is used for short runs.
* **A5 What the trainer does to a batch that the probe does not.** The trainer applies `ego.apply`, `dag.apply` (TR:3060-3061; both off at the defaults of the argv: `--ego-perturb`/`--dagger` flags absent) and `to_dev`; the model's p_gt schedule and per-step `torch.manual_seed` (TR:3097-3098) belong to the model's own losses. None of these touches `feats`, `frame_ok` or the three label arrays. The probe has no randomness after initialisation (no dropout).

## B. The training of the four probes (card section 2: "loss, batch size, number of steps, optimiser and learning-rate schedule of the arms of card ADD24")

* **B1 Optimiser.** `torch.optim.AdamW`, peak lr 3e-4 (`--lr`), weight decay 1e-2 on parameters with `ndim >= 2` and 0 on the others, the two groups of TR:2843-2848, one optimiser per arm (the gradient clip is per arm, so an arm's step does not depend on another arm's gradient). Defaults `--lr 3e-4 --wd 1e-2 --warmup 200 --clip-grad 1.0` are the parser's (TR:302-305) and are read from the parsed argv, not typed again.
* **B2 Schedule.** `TR.LRSchedule(a.lr, a.warmup, total)` (TR:756-766: linear warmup over 200 steps, then a cosine down to 0.1 x lr at `total`), set on every group before each step (TR:3095-3096). For a short run `total` is the short step count, as in the trainer with `--steps`.
* **B3 Clip.** `clip_grad_norm_` at 1.0 over the arm's trainable parameters (TR:3110). Float32, no autocast (the trainer's `--amp` is off in the argv).
* **B4 Loss.** `M.lead_sup_terms(out, batch, hist=5)` (M:781-802) on the probe head's output `[B, 12, 3]`, times `w_lead_sup` (1.0), the sum of the three parts (presence BCE, gap Huber, closing Huber) exactly as the model's total adds it (M:1392). ONE loss line in the tool (`loss = w * T["lead_sup"]`, tagged `# LOSS-LINE`); control p1's mutation rewrites it. Only the lead term is in the loss (card: "on the lead term alone").
* **B5 Probe architecture (card section 2).** Per-token network `Linear(1024, 128) - GELU - Linear(128, W)` with the SAME weights for each of the 40 tokens (the card says "a per-token network"), outputs concatenated in token order to a vector of 40 x W per frame; then `M.LeadSupHead(40 * W, 5)` (M:814-830; the class itself, imported, so the head is exactly the one of ADD24: per-frame linear to 64, concatenation of 5 frames, 320 to 128 to 3). Arms: TK16 (W 16, 640 per frame), TK64 (W 64, 2,560 per frame); init seeds 0 and 1: `torch.manual_seed(seed)` is called immediately before each arm is built (token network first, then head), so an arm's initial weights depend on its seed and shape only. Names `TK16_s0 TK16_s1 TK64_s0 TK64_s1`.
* **B6 Input normalisation (decision, not in the card).** The tokens are normalised per token over the feature axis by `F.layer_norm` WITHOUT parameters before the per-token network (`--input-norm ln`, the default; `none` skips it). Reason: the model's own adapter starts with a LayerNorm of the same axis (M:988) and the FUTTOK target does the same without parameters (M:966), so the probe sees the tokens on the scale the model sees; raw DINOv3 token scale is not known on this box (the real cache is on the pod only). It adds no parameter and no label. The lead can set `none` before the run; the choice is recorded in the checkpoint, the train log header and the extract record.
* **B7 Control parameter.** Every probe holds a scalar `ctrl` (zeros, registered, never used in the forward and not given to the optimiser). Its gradient is None, read as exactly 0.0 in the log (p1).
* **B8 Controls p3 (shuffle) arm.** `--shuffle-closing-labels`: the FINITE entries of the closing-speed label array of the built dataset (`ds.lead_sup_labels["clos"]`, indexed by join row, D:673) are permuted among the rows that have a finite closing label (`numpy.random.default_rng(12345)`); the mask (which rows carry a label) is unchanged, so the label counts in the loss are the same, and the value-to-row assignment is random. Only the closing labels move; gap and presence stay. The arm is TK16 with seed 0 under the name `TK16SH_s0`; the short run is 2,000 steps (card p3). Its held-out M1 is read by the reader after `extract`; the card's bar (at most +0.02) is applied by the lead from the reader's output.
* **B9 Train log (p5).** Per arm `<out>/<ARM>/train_log.jsonl`, first line a header (argv sha, widths, seed, norm, label counts and sha256, steps), then one record every 50 steps (the trainer's `--log-every`, TR:314) and at the last step: `lead_sup`, `lead_sup_bce`, `lead_sup_gap`, `lead_sup_clos` and `n_pres`, `n_gap`, `n_clos` of that step's batch (instantaneous, as the trainer logs), the interval MEANS of the four terms and the interval minimum of `n_gap`, the gradient sums `g_tok`, `g_head`, `g_ctrl` (absolute sums over the parameters of the per-token network, the head and the control; read after backward, before the clip) and lr. `check-log` implements p5: for every arm, the mean of the interval means over the records with step in the last 1,000 steps below the same over the first 1,000 steps, and `n_gap` (instantaneous) and its interval minimum above 0 at every record.
* **B10 Checkpoints.** One `<out>/<ARM>/ckpt_last.pt` per arm at the last step (kind `tokprobe`, state dict, widths, seed, norm, step, argv sha), then `<out>/TRAIN_DONE.json` last. No resume: a stopped run is rerun (about one hour; the pod script refuses to start over a finished marker, not over a partial one).

## C. `extract` (card section 2 "Outputs per arm"; layouts of `extract_states.py` and `pod_lead_apply.py`)

* **C1 State file.** For a split, clips are positions lo..hi-1 of the ascending `sha12` order of the split manifest (ES:55-57), eval 0:141 of the eval cache, train 600:1800 of the train cache (card; the defaults). Per clip: `torch.load(cache/split/clips/<clip>.pt)["pool4x10"].float()` (ES:62-63) to `[T, 40, 1024]`, the probe's projection (the same `project` as in training, in chunks of 256 frames) to `[T, 40 * W]`, stored float16 (ES:66). Fields `Z`, `clip_idx` (int32 index into `clips`), `t` (int16), `clips` (ES:72-74) and the record `<ARM>_<split>.npz.json` with the fields of ES:75-77 (`ckpt`, `ckpt_sha256`, `step`, `wm_state` = `"tokprobe"`, `wm` = `"tokprobe"`, `D` = 40 * W, `n_frames`, `n_clips`, `split`, `lo`, `hi`, `n_manifest`, `out_sha256`, `written_utc`, `seconds`) plus `arm`, `W`, `probe` = `tokprobe`. Written record last. Cache read with `weights_only` default as ES does.
* **C2 Lead outputs.** As `pod_lead_apply.py` (PA:105-131): the probe's own head applied to the float16 `Z` of the file cast to float32 (R3 of `LEADSUP_READ_DEFS.md`), for every row that has 4 predecessors t-1..t-4 of the same clip (the copy of `history_rows`, PA:40-52; a test asserts it equals the original), NaN elsewhere. Files `<ARM>_<split>_lead.npz` (`presence_logit`, `gap_m` = out x 50, `closing_ms` = out x 10, `has_history`, `hist`), `<ARM>_<split>_lead.npz.head.npz` (six tensors `frame_w frame_b mlp0_w mlp0_b mlp2_w mlp2_b` float32 and `hist`, PA:28-29 names, taken from the checkpoint), `<ARM>_<split>_lead.npz.json` with the keys of PA:125-128 (`ckpt_sha256`, `states_sha256`, `out_sha256`, `head_sha256`, counts, `cfg_lead` = {lead_sup on, w_lead_sup, lead_hist 5, lead_sup_detach "tokprobe"}, `plumbing` False). The same checkpoint sha256 is in all four records of an arm (check a1 of the reader).
* **C3 Device.** `extract` uses the GPU when present for the projection and the head, otherwise the CPU; the stored `Z` is float16 either way and the head outputs are computed from the stored `Z`, so the reader's forward on `Z` reproduces them (test, 1e-4).
* **C4 No label on the read path (p4).** `extract` and the probe forward never open a label array; a test replaces the label function by noise and compares outputs byte for byte.

## D. Things this tool does not do

* It does not compute M1 to M4, DELTA, the paired difference or the floor (the reader `leadsup_read_n1.py` and the lead do). It does not name an outcome. It does not read or write git, the pod, box 2 or a GPU on the dev box.
* The card's `p6` (the reader's controls k1, k2, k3-closing, k3-slot, k4 for every probe arm) are run by the reader on the pulled files, not here. The k3 permutation and k4 noise are the reader's.
* The reader's `ARMS` tuple is `LS/LSH/LSD` names; reading `TK*` arms needs its arm list extended (`--arms` takes a comma list and `arm_files` is name-generic in `leadsup_read.py`; `run`'s type grouping may need the lead's or the reader author's attention: listed in HANDOFF.md).

## E. Limits (as the card, section 7)

A probe on the pooled tokens says what the pooled tokens allow, not what the model does; the two seeds of a probe arm differ in initialisation only (same batches); 429 scored windows of 48 episodes; one corpus. The LayerNorm of B6 is a preprocessing choice the card does not state.
