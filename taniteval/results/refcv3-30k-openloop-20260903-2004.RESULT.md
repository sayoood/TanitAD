## 0. BINDING - everything here is OPEN LOOP (PI ruling, 2026-09-02)

> "The open loop performance corresponds ... to the fact that the ai model ... is not controlling the
> vehicle in the world. The fact that the predictor is consuming the output of the planner of the
> World model based system is also OPEN loop because the trajectory of the model is not affecting the
> new ego data ... Closed loop means that the trajectory is controlling the vehicle in the
> simulation, this can be done e.g. in AlpaSim or in a real test vehicle."

Every arm below is **OPEN LOOP**. refcv3 has **no `cl` arm and no `ol` arm** - not omitted, structurally
ABSENT: `RefCV3Model.forward` (`stack/tanitad/refs/refc_v3.py:480`) has **no action argument**, so there
is no action to feed back and no loop to close. The refav1 `cl` arm and this `os` arm are **both open
loop**, which is exactly why they are comparable - through each arm's **margin over the shared `ha0`
floor**, never as levels (`D-HF-COMPARABILITY`).

## 1. HEADLINE - the honest two-line verdict

**refcv3 BEATS the constant-velocity floor `ha0` on ADE: `os - ha0` = -0.1924 m [-0.2525, -0.1379],
separated, n=4823 windows / 141 episodes.** The deployment arm (nav withheld) also beats it:
`os_navzero - ha0` = -0.1689 m [-0.2312, -0.1109], separated.

**But refcv3 LOSES to the hold-action control `ha`, decisively and on every longitudinal metric:
`os - ha` = +0.1803 m [+0.1563, +0.2047] ADE, separated** (positive = refcv3 worse). Holding the last
observed action for 2 s is a *better* trajectory predictor than the 107 M-parameter model on this grid.
`ha - ha0` = -0.3727 m, i.e. the model recovers only about **half** of the margin the trivial
hold-action control already achieves. **Beating `ha0` is therefore necessary, not sufficient, and the
`ha` comparison is the one that should be read as the bar.**

### 3.3 The two VOID-RISK flags, and why neither voids this read

The tool raised two, and both are **expected by construction**, not defects:

* `os` bit-identical to `oracle_sel` on **2700/4823 (55.98 %)** - this IS the measurement
  `agrees_with_oracle = 0.5598`: on those windows the model's own `sel_score_v3` choice happens to be the
  GT-nearest anchor. `REFCV3_ARM.md` section 2.6 records ~57 % for the clean era. Not two arms collapsing -
  one real quantity.
* `os` bit-identical to `os_navshuf` on **2417/4823 (50.11 %)** - the permutation only **changed** the
  token on 2,406 windows; the rest are identical *because the shuffle was a no-op there*. The spec's
  fixture shows the same arithmetic (17/42 = 42 - 25).

**Cross-call caveat (spec section 2.8):** `os_navzero` comes from a **separate** forward (nav_cmd=None is a
whole-call property), so a float32 batching floor of ~6e-7 m sits under it and `identical_to` at 1e-9 m
cannot resolve it. A real nav difference is ~4.7e4x that floor. `identical_to` is therefore read for
`os`-vs-`os_navshuf` only and ignored for `os`-vs-`os_navzero`.

### 5.6 STRATEGIC - route head vs the v2.1 route label, under three nav conditionings

`paired_true_minus_shuffled_accuracy` = **0.0 [0.0, 0.0]** - the route head's predictions are
**byte-identical under all three nav conditionings.**

**This is a POSITIVE finding and it is the anti-echo result.** On the **1,736 windows whose nav token
actually changed**, the predicted route follows the **LABEL** on **0.7414 [0.6777, 0.8047]** and the
**fed (wrong) shuffled nav** on only **0.2224 [0.1912, 0.2542]**. The tool's own reading: "an ECHO reads
follows_nav ~ 1 / follows_label ~ 0; route skill from vision reads follows_label high regardless of the
token." refcv3 reads the second pattern. **The route head is NOT an echo of its own nav input** - unlike
flagship v1's, which scored 1.0000 on a bijection of the fed nav.

The mechanism is in the run's own `config.json`: `goal_provenance.inference_inputs = ["pooled
(mean-pooled conv features, last frame)"]` and `contains_situation_classifier_output: false`. The route
head reads **pooled vision only**, which is why it is nav-invariant, and it satisfies the PI's
2026-08-03 information-disjointness rule by construction.

Kappa 0.4659 against a 0.6742 majority rate is **real skill above the majority class**, and it **survives
deployment** (nav withheld) unchanged. Per-class recall is weakest on `route_left` (0.3447).

## 7. Instrument defects FOUND AND FIXED during this read

Both were latent in code the spec marked UNVERIFIED, and both are now staged with tests green.

**D1 - `oracle_sel` / `a_star` crashed on GPU (device mismatch).** `anchors_bank` was left on the model's
device while `traj_tgt` and `sv` are CPU dataset tensors, so the `a_star` argmin raised
`Expected all tensors to be on the same device`. The spec's fixture ran **CPU-only**, so this path had
never executed on CUDA. It is on the **main** path, not only under `--with-oracle-sel` (both branches
compute it). Fixed by keeping the 128-anchor bank on CPU - the argmin is tiny and this reproduces the
CPU semantics the fixture validated. `taniteval/tools/refcv3_arm.py`.

**D2 - the lead-block join silently lost the ENTIRE distance-keeping family.** `join_lead_block` keys on
`(clip_id, 2t)` - correct for refav1 (5 Hz provider over a 10 Hz block). refcv3's B1 cache is **already
10 Hz**, so the adapter compensated with `ws' = (ws + raw_off) // 2`; that integer division **truncates
every ODD raw frame to frame-1**. A one-frame (0.1 s) error is worth ~0.24-0.44 m/s of speed, so the
label-free speed proof correctly **refused all 141 episodes** and the family came back REFUSED with
`NO_LABEL 4823`. This is exactly the WORK ITEM named in `REFCV3_ARM.md` section 4.1.

Fixed by giving `join_lead_block` the **frame-identity mode** the spec asked for: a new keyword
`frame_of_t`, **defaulting to the existing `2*t`** so refav1 is untouched, with refcv3 passing identity
and shipping the true raw frame in the shim.

**Evidence the fix is real, not just non-crashing:**

| | before | after |
|---|---|---|
| episodes OK | **0 / 141** | **141 / 141** |
| coverage | NO_LABEL 4823 | LEAD 1489 / NO_LEAD 1145 / NOT_STRAIGHT 1889 / NO_LABEL 300 |
| label-free speed proof | **0.444514 m/s** (refused) | **0.000026 m/s** |
| distance_keeping | REFUSED | **PRESENT** |

ADE and every other family row are **byte-identical before and after**, as they must be - the join
touches only distance-keeping.

**Regression evidence:** `stack/tests/test_refcv3_arm.py` **20 passed** (the spec's documented baseline),
and `test_refav1_arm.py` + `test_refav1_lead_block.py` **26 passed** - so the refav1 `2*t` default is
provably unchanged.
