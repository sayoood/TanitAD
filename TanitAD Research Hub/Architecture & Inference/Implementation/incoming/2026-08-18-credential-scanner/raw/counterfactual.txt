CONCLUSION
==========
Row 1 is the finding: the EXISTING scanner catches the exact C111 shape (an hf_ token
on line 11 of a rescued *.log). C111 was therefore NOT caused by a missing scanner --
it was caused by a scanner that NOTHING CALLED. That is C108's class, and the
2026-07-26 program harvest had already recorded safe_commit.py as
"imported_by: Nothing" at DECISION-GRADE.

The two genuine gaps in the old scan:
  (a) generic high-entropy assignment to api_key/token/secret/password -- not covered;
  (b) BINARY blobs -- `git diff --cached` emits "Binary files ... differ" with NO
      content lines, so a token inside such a blob was STRUCTURALLY INVISIBLE.
      The new scanner reads staged BLOBS via `git cat-file --batch` instead.

NOTE ON THE `--tree` COLUMN
===========================
An earlier cut of this table showed `--tree` MISSING the binary case while `--staged`
caught it, because the tree walker's skip list carried `.bin` (chosen for byte volume).
Those containers are UNCOMPRESSED -- an ASCII token survives verbatim inside them.
The skip list was narrowed to entropy-coded formats only, where a plaintext pattern
provably cannot exist. The table above is the post-fix measurement.
