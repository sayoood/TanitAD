
## 2. ⭐ The eval-side seam, and the two arguments that carry it

```python
# eval_flagship_v4.build_v2_val_episodes
rec  = parity.assert_v2_parity_cache(dirs, label="--v2-val-cache", require=a.require_parity)
eps  = build_v2_providers(dirs, lru_size=a.v2_lru, frame=slice_frame, verbose=verbose)
bind = parity.assert_v2_geometry_matches(rec, train_frame, label="--v2-val-cache",
                                         providers=eps, parent=cache_frame)
```

* `frame=` makes the providers deliver the **sliced** raster;
* `parent=` makes the binding compare the shape they **hand back** against the frame the eval
  **declares** — so a sub-frame that is configured and never applied is a refusal before the
  first window, not a published ADE.

⭐ **`--frame-*` describes the CACHE; `--v2-subframe` describes the MODEL** — the same split the
trainer uses, because it is the same function.

## 3. ⛔ THE `ego=` SHAPE, CLOSED — and demonstrated failing, not asserted

### 3.1 The guard

`parity.assert_eval_frame_matches_run(run_cfg, frame, *, cache_frame, label)` reads the run's own
`config.json`, which the v5 trainer writes in two blocks:

* `geometry` — the frame the **MODEL** saw (post-`apply_frame`, i.e. the sub-frame on a sliced run);
* `geometry_cache` — the frame the **BYTES** are, `null` when the run did not slice.

It refuses on any mismatch and the message **names the flag value that reproduces the run**:

```
FRAME VIOLATION [--ckpt vs eval frame] — SCORING A CHECKPOINT ON A FRAME IT WAS NOT TRAINED ON
  trained on : 176x624 px, f_ref 305.5775, cylindrical   (176x624f305.5775cyl)
  eval reads : 256x640 px, f_ref 305.5775, cylindrical   (256x640f305.5775cyl)
  …
  Reproduce the run's frame:
      --v2-subframe 176x624
```

Three properties worth stating because each was a decision:

1. ⭐ **It is on the CLI path, before the checkpoint is opened.** `test_the_frame_guard_fires_
   from_main_BEFORE_the_ckpt_is_loaded` drives `main(argv)` with a checkpoint path that **does
   not exist** and requires the `ParityViolation` to arrive first. Its GREEN twin
   (`…_ACCEPTS_the_matching_frame_and_then_reaches_the_ckpt`) requires `main` to get *past* the
   guard and fail on the missing file — so the guard is neither absent nor unconditional.
2. **Both directions.** A sliced run scored on the parent is refused **and** an unsliced run
   scored on a slice is refused, with a different remediation line (`--frame-h/--frame-w`,
   because `geometry_cache` is `null`).
3. ⛔ **A pre-geometry checkpoint is NOT silently passed and NOT refused.** Every arm before
   2026-07-27 has no `geometry` block; refusing would make the historical record unreproducible.
   It returns `checked: false` and the harness prints `⚠ FRAME UNVERIFIED: …`.

## 8. The encoder's share of a full training step

`code/bench_encoder_share.py` + `code/merge_encoder_share.py` on pod2's A40, real
`WorldModel` + `FlagshipV4Head` + `GoalScalarHead` + AdamW, a **real batch off the registered v5
val cache**, `v4_loss_step` → `backward` → clip → `opt.step()`. Data loading is **outside** the
timing (one batch pulled and reused on device). Arms are interleaved, rotated across two passes,
warm-up discarded.

⚠️ `v4_loss_step` calls `world.encode_window` **twice** — the observation window (8) **and**
`plan.needed_fut` (10 frames) — so the encoder sees **`batch × 18`** images per micro-batch, not
`batch × 8`. That is the first thing that makes the encoder's share larger than it looks.

### 8.1 🔴 THE FINDING THAT CAME OUT OF IT: `--batch 16` DOES NOT FIT

MEASURED capacity probe — one REAL step per rung, `grad_checkpoint=False` (the config default),
pod2 A40, **45 498 MiB** total. Raw: `raw/capacity_{256x640,176x624,128x576}.json`.

| frame | tokens | **max micro-batch** | peak at max | OOM at | peak @8 |
|---|---:|---:|---:|---|---:|
| **256×640** (the cache as built) | 640 | **8** | 34 470 MiB | **16, 12** | 34 470 MiB |
| **176×624** (rig-clean) | 429 | **12** | 35 116 MiB | **16** | 25 996 MiB |
| 128×576 | 288 | **16** | 32 361 MiB | *(none)* | 19 061 MiB |

⇒ **the staged v5 command's `--batch 16` OOMs at BOTH candidate frames on a 44 GB A40.**
It would have died after the model build and the first data fetch, at step 0.

Two things make this non-obvious and worth stating:

* ⛔ **`train_flagship_v4.py` has no `--grad-checkpoint` flag.** `train_flagship4b.py` does — and
  its own docstring example uses it (`--batch-size 16 --accum 4 --grad-checkpoint`). So the GPU
  memory lever v1 trained with is **not reachable from the v5 trainer at all**.
* The fix needing **no code change** is `--batch 8 --accum 8`: effective batch stays **64**,
  which is v1's and the value the trainer's own launch banner checks (*"same-as-v1: micro-batch
  × accum = EFFECTIVE 64"*). That is what §7.1 uses.

⭐ Note the sub-frame **buys back the batch**: at 176×624 the same `--batch 8` peaks at
**25 996 MiB** instead of 34 470, and 12 becomes reachable.

### 8.2 ⭐ The measurement — matched at micro-batch 8, the largest that fits at 256×640

Raw: `raw/encoder_share_2026-07-27.json`. Six runs (3 arms × 2 rotated passes), 8 timed reps
each after 3 discarded.

| frame | tokens | images/step | **full step s** | spread | **encoder-only s** | spread |
|---|---:|---:|---:|---:|---:|---:|
| **256×640** | 640 | 144 | **1.6944** | 0.45 % | **1.1220** | 0.13 % |
| **176×624** | 429 | 144 | **1.2988** | 0.19 % | **0.7543** | 0.12 % |
| 128×576 | 288 | 144 | **1.0835** | 6.37 % | 0.5101 | 0.09 % |

**⭐ THE PRIMARY, and it needs no decomposition — it is the ratio of two REAL training steps:**

| frame | **run-level step ratio** | encoder-only ratio | **encoder share of a full step** |
|---|---:|---:|---|
| **256×640** | 1.000 | 1.000 | **0.662** |
| ⭐ **176×624** | **0.7665** | 0.6722 | **[0.581, 0.712]** |
| 128×576 | **0.6394** | 0.4546 | [0.471, 0.661] |

**Read it as:** ⭐ **the rig-clean frame costs 0.767× a full training step — not 0.68×.** The
encoder is ~2/3 of the step, and the other third does not shrink, exactly as
`RIG_FIX_WIRING.md` §5.2 warned. Anyone quoting a v5 GPU-hour saving must use **0.767**, not the
encoder ratio.

Two consistency checks that make this more than one number:

* ⭐ **The encoder-only ratio reproduces the rig-fix stream independently.** They measured
  **0.676–0.703×** on a synthetic image-batch sweep; this measures **0.6722×** inside a real
  `v4_loss_step` on real cache bytes at a different batch shape. Different instrument, same
  answer.
* **The share and the step ratio are mutually consistent.** From the 256×640 share (0.662) and
  the encoder ratio (0.672), the predicted step ratio is `1 − 0.662 × (1 − 0.672) = 0.783`;
  measured **0.767**. 2 % apart, in the direction a standalone encoder timing is expected to be
  biased.

⚠️ **The share is a BRACKET, not a point.** The two estimators — encoder timed standalone ÷ step,
and the share implied by the step ratio — measure the same quantity by different routes, and a
standalone timing does not reproduce the kernel overlap or memory pressure the encoder sees
inside the step. Reporting one of them as *the* share would be over-claimed.

⚠️ **128×576's 6.37 % pass-to-pass spread** is ~30× the others and its two samples (1.049 /
1.118) bracket the ratio meaningfully. Its `0.6394` is an indication; `176×624`'s `0.7665`
(0.19 % spread) is tight.

### 8.3 The first GPU-hour figure for the arm — ESTIMATED, with both biases named

No whole-step v5 number existed in the program (`V5_TRAINER.md` carries no GPU-h estimate), so
there is nothing to revise. At **30 000 optimizer steps × accum 8** on one A40:

| frame | ESTIMATED GPU-h | vs 256×640 |
|---|---:|---:|
| 256×640 | **≈ 113** | — |
| ⭐ **176×624** | **≈ 87** | **−26 GPU-h** |

**Class: ESTIMATED**, derived from the MEASURED per-micro-batch step times. Two biases, in

## 9. 🔴 ESCALATIONS — decisions, not documentation

1. 🔴 **`--batch 16` does not fit at either candidate frame on a 44 GB A40** (§8.1: max micro-batch
   **8** at 256×640, **12** at 176×624, **16** only at 128×576). Launch with `--batch 8 --accum 8`
   (no code change, effective batch 64 preserved — this is what §7.1 uses), **or** add a
   `--grad-checkpoint` flag to `train_flagship_v4.py` — it has none, while `train_flagship4b.py`
   does and v1's own documented command used it. **A PI/orchestrator decision before the go, not
   after**: as staged, the run dies at step 0 after the model build.
   ⚠️ This was measured on **pod2's A40 (45 498 MiB)**. pod1 is an **A6000 (~48 GB)** — 6 % more,
   against a 256×640 requirement that exceeds 44 GB by more than that at batch 12, so the same
   conclusion is *expected* to hold there. **Not measured on pod1** (it is training and was not
   contacted).
2. ⚠️ **`--print-launch`'s `PREFLIGHT: OK` does NOT run the parity check.** MEASURED: it printed
   `PREFLIGHT: OK` for `--require-parity` against a directory whose corpus key resolves to
   `None` (§5.1). `preflight_asserts` is purely argument-level — it verifies the *flag is
   present*, never that the cache *passes*; `parity.assert_v2_parity_cache` runs inside `train()`.
   **So a `--print-launch` OK is not evidence a launch will start.** One-line fix (call the
   cache guard from `preflight_asserts` when the v2 dirs exist) — **not made here**, because it
   touches the launch path and the PI owns the launch.
3. ⚠️ **The v5 wide cache has 2 400 clips; the raw parity corpus trains on 2 376 episodes.** The
   24 clips that fail to decode in the raw epcache build **decoded successfully** in the 120°
   PNG v2 build (`missing_count: 0`, `membership_identical: true` on both splits). The
   registration accepts this under its own published rule, and the manifest records
   `episode_count: 2400`. **v5 will therefore train on ~1 % more episodes than every prior arm.**
   That is a cross-arm comparability fact that belongs in `MODEL_REGISTRY.md`'s v5 row; nobody
   has decided whether it should be equalised.
4. ⚠️ **The corridor co-primary emitter is UNVERIFIED on the v2 corpus.** `run_gate.py check`
   takes `--corridor-json`, and `eval_flagship_v4.py` does not produce it. Whether *that* emitter
   can read a v2 cache is exactly the question this stream answered for the ADE primary, and it
   has not been asked. **Owner needed before the gate step, not at it.**
5. ⚠️ **`train_flagship4b.py` still has no sub-frame flag** (inherited, rig-fix escalation #4).
   pod1 is mid-run and its sha256 is pinned. One-line change when pod1 is idle, pin updated in
   the same commit. **Noted, not done.**
6. ⚠️ **A third v2 decode implementation exists** (`scripts/slice_v2_cache.py`, §1.2) and was
   named in neither prior count. It is not on any training or eval path today, but it is the
   next place a geometry fix would have to be applied a third time.
