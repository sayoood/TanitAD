## 1. 🔴 The gap was WIDER than "no trainer passes it"

The escalation in `RIG_CLEAN_FIX.md` §9.1 says the fix is a loader argument that no trainer passes.
**Measured here: the fix is not on the v5 trainer's code path at all.**

```
verified fix   : scripts/v2_compressed.py :: load_compressed(path, frame=…)
v5 trainer     : scripts/train_flagship_v4.py
                   └─ tanitad/data/v2_dataset.py :: build_v2_providers()
                        └─ V2CompressedCache.decode_stacked_range()
                             └─ _decode_stacked()          ← decodes + stacks HERE
```

`v2_dataset.py`'s own module docstring says it *"deliberately does NOT import
`scripts/v2_compressed.py` (whose build path pulls pandas / pyav)"* — it **mirrors**
`load_compressed` instead. So `load_compressed(frame=…)` could have been passed by every caller in
the repo and v5 would still have trained on the rig-asymmetric frames. Adding the argument at the
trainer would not have worked; the argument had to be added to the *other* implementation.

⇒ **"Wire the fix in" was not one line. It was one line in a function nobody had noticed was a
second copy.** Three greps establish it: outside `tests/`, `load_compressed` has **exactly ONE call
site** — `v2_compressed.measure`'s own round-trip validator — and **0** in either trainer;
`build_v2_providers` is *called* from **exactly two files**, both trainers (`parity.py` names it in
prose only); and no evaluator anywhere calls either (§7.3).

### 1.1 What was changed

| file | change |
|---|---|
| **`stack/tanitad/data/v2_dataset.py`** | `build_v2_providers(…, frame=None, allow_lossy=False)`; `V2CompressedCache(frame=…)` resolves the `(rows, cols)` **per clip against that clip's own stored geometry** and caches it in the payload LRU; `_decode_stacked(…, sl=…)` slices each raw frame **before** stacking (the order `load_compressed` uses; spatial slice and channel concat commute, so it is bit-identical and cheaper); `stored_frame_of(payload)`; `_assert_subframe_deliverable()` fails **at launch**, off the first clip's real bytes, instead of inside a DataLoader worker minutes in. Every provider's `.frames.shape` reports the **sliced** raster. |
| **`stack/scripts/train_flagship_v4.py`** | `--v2-subframe HxW\|none`; `parse_subframe()`; `resolve_v2_frames()` (⭐ the seam: derives the sub-frame **from the parent** via `centred_subframe`, so `f_ref`/projection are *copied*, and applies it to `cfg` so the **encoder moves with it**); `build_v2_data()` (extracted so the call itself is testable); `[RIG-CLEAN]` preflight; `--v2-subframe` preserved through `_staged_command`; `config.json` gains a `geometry_cache` block. |
| **`stack/tanitad/data/parity.py`** | `assert_v2_geometry_matches(…, parent=…)`: **SHAPE** is bound to the sub-frame (what the providers actually deliver), **DECLARATION** to the parent (what the builder recorded), and the sub-frame must be a real centred slice of the parent — recorded as `sliced_from` with the exact rows/cols. |
| **`stack/tests/test_v5_frame_wiring.py`** | new, 437 lines, 24 tests. |

`385 insertions, 48 deletions` across the three existing files.

⛔ **`scripts/train_flagship4b.py` was NOT touched** — pod1 is mid-run on it and
`test_train_flagship4b_is_untouched_by_this_change` pins its sha256. It reads `build_v2_providers`
too, so it *could* take the flag; that is an escalation (§7.4), not a change made while an arm runs.

### 1.2 ⭐ Why the frame is now hard to lose — the structural part

`resolve_v2_frames` sizes the encoder for the SUB-frame. `build_v2_data` passes the SUB-frame to
the loader **and** hands the binding the parent. So:

* if the loader is not told → providers return `256×640`, the shape binding sees `176×624` declared
  and **refuses the launch**, naming the call that must change;
* if the flag is not typed at all on a non-deployed frame → **preflight blocks**, and names the
  measured rig asymmetry and both admissible values;
* if the sub-frame is not a real slice (odd margin, changed focal, grown frame) → `centred_subframe`
  / `subframe_slice` refuse before any GPU work;
* if the cache is **lossy** → refused, because a JPEG slice is not what a rebuild produces.

The declaration cannot be inert. That is the property the last three failures lacked.

## 5. The token and compute consequence — stated, and re-measured

### 5.1 Tokens

**640 → 429, a 33.0 % cut** (`16×40` → `11×39` at patch 16). Read off `cfg.encoder.token_grid()`
**after** the real seam ran against the real cache, not computed from the flags.
`state_dim` stays **2048**. `128×576` gives **288 tokens (−55.0 %)**.

### 5.2 ⭐ Compute — re-measured at the v5 config, because the inherited number was not it

The rig-clean stream measured `0.647×` on `base250cam_config()` at image-batch 8 with no autocast.
v5 trains `flagship4b_config()` under AMP, and its encoder sees `batch × window = 16 × 8 = **128**`
images per micro-batch. `code/bench_encoder_v5_config.py` on pod2's A40, bf16 autocast, 10 reps.
Raw: `raw/bench_encoder_v5_2026-07-27.json`.

| frame | tokens | ms/image @16 | @32 | @64 | **ratio @16 / @32 / @64** | peak MiB @64 |
|---|---:|---:|---:|---:|---|---:|
| **256×640** (built) | 640 | 8.232 | 8.020 | 7.848 | 1.000 | 15 003 |
| ⭐ **176×624** | **429** | **5.784** | **5.573** | **5.307** | **0.7026 / 0.6949 / 0.6762** | **10 359** |
| 128×576 | 288 | 4.124 | 3.765 | 3.595 | 0.5010 / 0.4695 / 0.4581 | 7 288 |

⇒ **The encoder's forward+backward costs 0.68–0.70× at the clean frame, and peak activation memory
0.69×.** The saving grows with batch (attention is quadratic in tokens), so the larger real
micro-batch sits at the favourable end.

⛔ **Scope, stated so it cannot be rounded up: this is the ENCODER only.** The predictor, the four
brains, the grounding and the anchored planner do not shrink with the token count, so the **run-level
saving is strictly smaller than 0.68×**. Anyone restating the v5 GPU-hour budget must apply the
ratio to the encoder's share of the step, not to the step. *(No whole-step v5 number exists in the
program yet — `V5_TRAINER.md` carries no GPU-h estimate — so there is no prior figure to revise;
this is the first compute record for the arm, and it is favourable.)*

Encoder parameter count moves only in the positional embedding: **87.318 M → 87.156 M** (176×624)
/ 87.047 M (128×576).

### 5.3 ⚠️ SELF-CORRECTION — the data-loader cost, and a confound I nearly published

My first measurement timed `load_compressed(parent)` then `load_compressed(sub)` on the same file
and read the slice as **22.7 % FASTER** (0.9773 s vs 1.2644 s). **That number is confounded**: the
second call runs against a warm page cache. It is in `raw/wiring_verify_176x624.json` under `L6_cost`
and must not be quoted.

`code/time_window_decode.py` measures the path training actually uses —
`decode_stacked_range` over a window-sized range — with the arms **interleaved and rotated** so no
arm is always first, the page cache pre-warmed for all, and one rep discarded.
Raw: `raw/window_decode_timing.json` (6 real val clips, 5 reps).

| arm | median s/clip | min–max | ratio |
|---|---:|---|---:|
| parent `256×640` | **0.1937** | 0.168–0.209 | 1.000 |
| `176×624` | **0.2053** | 0.189–0.234 | **1.059** |
| `128×576` | 0.2220 | 0.183–0.243 | 1.146 |

⇒ **the slice costs ≈ +6 % on the decode, ~+0.012 s per window fetch — and the ranges overlap
heavily, so this is an indication, not a tight estimate.** It is CPU work in 8 DataLoader workers,
overlapped with the GPU, against a −30 % encoder cost. ⚠️ It is also **not** the RIG_CLEAN_FIX's
"+0.113 s/clip", which is a *whole-clip* `load_compressed` and a different unit entirely.

## 7. 🔴 ESCALATIONS — decisions, not documentation

1. 🔴 **NEITHER WIDE CACHE IS REGISTERED.** `parity_manifest.json` has two corpora, both the
   original splits, both `geometry: null`. `--require-parity` — mandatory for a v5-class run — will
   **refuse** at launch. Runbook steps 2/3 must run, **now that the manifests are correct**.
2. 🔴 **THE TRAIN CACHE DIR CANNOT RESOLVE ITS KEY.** It is `/workspace/data/pai_wide120_v2png_train`.
   `register_v2_geometry_sibling` explicitly refuses a key that is not a substring of the cache path
   (*"the registration would be INERT and the trainer would read the cache as NON-PARITY"*), and
   `corpus_key_of` resolves by path substring. **The directory must be renamed to
   `physicalai-train-e438721ae894-w120-256x640cyl` before registration.** The val dir is already
   correctly named. ⚠️ Renaming invalidates nothing — the `_v2manifest.pt` sidecar does not exist yet.
3. 🔴 **NO EVALUATOR CAN READ A V2 CACHE — so a v5 checkpoint is trainable but not evaluable.**
   Two probes: `scripts/eval_flagship_v4.py` takes only `--val-cache` (raw epcache) and contains
   **one** line matching `v2|frame_h|geometry`; and `build_v2_providers` is *called* from **exactly
   two files in the whole repo**, both trainers — none in `scripts/eval_*`, none in `taniteval/`.
   The raw epcache at this geometry is ~697 GB and fits on no host, so this is not a "point it at the
   other cache" fix. **Owner needed before the run finishes, not after.**
4. ⚠️ **`train_flagship4b.py` reads `build_v2_providers` and did not get the flag.** Deliberate:
   pod1 is mid-run on it and its sha256 is pinned by a test. If any future v2 arm launches from that
   trainer it will silently train on the un-sliced frames. One-line change, to be made when pod1 is
   idle, with the pin updated in the same commit.
5. ⚠️ **The PI still chooses the frame.** `176×624` is the stream's recommendation and this wiring's
   default *example*, nothing more — `128×576` is verified end-to-end here too (§2) and is one flag
   value away. Nothing in the code prefers either.
6. ⚠️ **`--v2-subframe` does not, and cannot, prove the pixels.** It proves the raster the trainer
   receives and that it is a valid centred slice of a declared parent. Nothing hashes pixels
   (inherited, still open — `V5_TRAINER.md` §9.3).
